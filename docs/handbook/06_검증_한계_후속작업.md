# 검증 결과·한계·후속 작업

기준: 2026-10-08 KST, 현재 저장소의 `docs/player-explorer-design.md`, 테스트 코드 및 관련 구현을 대조해 작성했다. 아래 배포 직전 테스트 결과는 기존 작업 기록이다. 이 문서 작성 과정에서 전체 테스트를 다시 실행했다는 뜻은 아니다.

## 4. 리뷰에서 발견하고 수정한 사항

| 발견 사항 | 원인/위험 | 수정 |
|---|---|---|
| 긴 세로 보고서, 조작과 관계 없는 별도 시각 요소 | 그래프나 버튼이 있어도 사용자에게 탐색 결과가 명확하지 않음 | 3개 보기와 공유 필터를 한 작업 영역에 연결 |
| 하이라이트 속성의 따옴표 처리 | 특수문자 챔피언 이름이 HTML 속성 경계를 손상할 수 있음 | 이스케이프·안전한 키 인코딩 및 회귀 테스트 |
| 그래프 드래그 종료 시 표시 창 이동 | 선택 키는 남지만 창 시작점이 보존되지 않음 | 선택 키와 windowStart를 함께 전달·유지 |
| 모바일에서 숨겨진 라인 컨트롤로 포커스 복귀 | 지도와 모바일 버튼이 같은 선택자를 공유 | 보이는 요소를 우선 찾아 포커스 복원 |
| 선택 범위와 누적 시리즈 안내 혼동 | 같은 화면에 다른 범위의 수치가 표시됨 | 상단 및 계산 기준에 ‘현재 경기일 전체’/‘필터 적용 전’ 명시 |
| 더 보기 완료 후 포커스 손실 | 마지막 추가 후 버튼이 사라짐 | 남은 버튼 또는 경기 목록 제목에 포커스, 실제/데모 2개 영향 시나리오 확인 |
| 모션 끄기에서도 hover 이동 잔존 | transition 제거만으로 transform 자체는 제거되지 않음 | 명시적·OS 모션 설정에서 hover translation도 제거 |
| all-null/all-Perfect 그래프의 가짜 숫자 축 | 기본 축 상한이 실제 수치처럼 보임 | 수치 표본이 없으면 숫자 축 제거, Perfect 별도 표시 |

‘수정’은 해당 소스와 테스트 범위의 결과다. 실제 모바일 동작이 모두 검증됐다는 뜻은 아니다.

## 5. 다음 작업 우선순위

### P0. 실제 화면과 입력 검수

먼저 현재 v12를 실제 데스크톱 및 모바일에서 열어 검수한다. 새 장식 기능을 더하기 전에 사용자가 지적한 체감 문제를 확인해야 한다.

- 화면 폭: 1440 / 1024 / 390 / 320 CSS px. 브라우저 에뮬레이션과 실기기는 구별해서 기록한다.
- 기기/환경: 데스크톱 Chrome, 모바일 Chrome·Safari, 카카오톡 웹뷰. 각 환경에서 실제로 가능한 항목만 통과 처리한다.
- 탐색: MID → Ahri → KDA/CS·분/피해량 → 그래프 좌우 드래그 → 전체 타임라인 → 하이라이트 → 경기 목록 → 상세 통계.
- 터치: 세로 스크롤과 그래프 가로 조작이 충돌하지 않는지, 손을 떼는 순간 창이 튀지 않는지, 작은 버튼을 잘못 누르지 않는지 확인한다.
- 가독성: 긴 닉네임·챔피언명, 키보드 열린 상태, 기기 가로 회전, 200% 확대, 빈 데이터, 1경기, null/Perfect만 있는 그래프.
- 접근성: Tab 순서·방향키·Home/End·Esc·dialog 포커스 복귀, 모션 끄기, OS 줄이기, 선택 상태 음성 설명.
- 데모/실제: 진입·종료·뒤로/앞으로·새로고침. 어느 순간에도 가상 수치가 실제 전적으로 보이지 않는지 확인한다.

발견 사항은 화면·조건·재현 순서·기대 결과·실제 결과·심각도·수정 위치와 함께 남긴다. 스크린샷이 있더라도 드래그 감각과 실제 기기 성능을 검증했다고 확대 해석하지 않는다.

### P1. ‘재미’에 대한 사용자 재평가

가상 데이터가 있는 해람 프로필로 사용자에게 조작 설명을 최소화하고 관찰한다. 사용자가 첫 번째로 누른 요소, 그래프 조작 발견 여부, 다시 보고 싶은 경기, 화면이 여전히 보고서처럼 느껴지는 부분을 기록한다. 만족 응답을 받기 전에는 ‘재미 요구 충족’을 완료 상태로 쓰지 않는다.

후속 디자인은 위 관찰에 따라 결정한다. 애니메이션·배지·도식을 추가하는 양 자체를 목표로 삼지 않는다. 존재하지 않는 MVP·MMR·퍼포먼스 수치를 넣어 재미를 만들지 않는다.

### P2. 필요한 범위의 성능 검토

실제 데이터가 많아졌을 때 프로필 재집계·전체 recent 배열의 그래프 payload·반복 렌더 비용을 측정한다. 현재 24경기 데모만으로 대규모 성능을 보증하지 않는다. 병목이 확인되면 선택자 메모이제이션이나 표시 범위 최적화를 검토하되, 통계 중복 저장과 원천 불일치부터 만들지 않는다.

### P3. 자체 평점·내부 MMR은 별도 설계

현재 계산식이 확정되지 않아 Score, performanceScore, MVP, ACE, internalMMR을 생성하거나 표시하지 않는다. 미수집 영역에 0.0점 패널을 만들지 않는다.

연동하려면 다음 순서가 필요하다.

1. 사용자와 평가 목적·입력 항목·표본 최소치·역할 차이·결측 처리·공식 버전을 확정한다.
2. 추가 필드를 `history-core` 검증/복제, 버전형 JSON 스키마와 프롬프트, 통계 계층에 일관되게 연결한다. 기존 `damage`·`vision`을 다른 의미로 조용히 바꾸지 않는다.
3. `selectPlayer`/`selectGames`를 읽는 독립 서비스로 점수를 산출한다. 경기 기록 자체와 파생 평점을 구분한다.
4. 검증된 결과를 프로필에 노출한다. 임의 점수나 메달을 fixture 밖 운영 데이터에 넣지 않는다.
5. 팀 셔플이 이를 사용할지는 별도 결정한다. 현재 티어·주/부 포지션 기반 셔플에 개인 통계 가중치를 이번 작업으로 몰래 반영하지 않는다.

## 6. 완료 판단의 경계

현재 상태는 ‘개인 성적 탐색 기능 구현·선택된 자동 검증·배포 완료, 실제 렌더링/실기기와 재미 검증 대기’다. 다음 담당자는 미검증 항목을 완료로 승계하지 않아야 한다. 실제 기록·권한 정책을 수정하지 않고 데모를 이용해 먼저 확인하는 것이 가능하다.
