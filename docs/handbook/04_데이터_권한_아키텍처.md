# 데이터·권한·아키텍처

기준: 게시 v12, 커밋 `aca78cc8665f7a5be2aef674887fac9233187f5c`. 아래 코드 경로는 ZIP의 **`source/` 디렉터리 기준**이다. 이 문서는 실제 소스와 README를 확인하여 작성했다. 운영 DB의 내용을 조회하거나 복제한 문서는 아니다.

## 2. 저장되는 원천 데이터

`shared_state`의 `id=1` 한 행에 현재 경기와 기록 전체를 JSON으로 저장한다. `version: 1`, `archiveVersion: 1`은 앱의 저장 형식이며, 외부 경기 JSON의 `schemaVersion: 1`과 구분한다.

| 구조 | 주요 항목 | 의미 |
|---|---|---|
| 현재 상태 | `roster`, `mode`, `bestOf`, `draw`, `results`, `games`, `seriesId`, `matchDate`, `history` | 공용 경기와 선수 설정, 과거 기록의 원천. |
| 선수 | `id`, `name`, `tier`, `primary`, `secondary`, `excluded`, `active`, `currentNickname`, `nicknameAliases` | 통계 연결은 불변 `id`로 한다. 이름·닉네임은 표시/입력 연결용이다. |
| 세트 | `winner`, `draw`, `durationSeconds`, `externalId`, `notes`, `players` | 실제 치른 한 판. `draw.teams`의 선수 ID와 `role`이 당시 팀·실제 포지션이다. |
| 세트 선수 측정치 | `id`, `champion`, `nicknameAtMatch`, `kills`, `deaths`, `assists`, `damage`, `cs`, `gold`, `vision` | 측정하지 않은 항목은 `null`. 현재 닉네임과 당시 닉네임을 분리한다. |
| 종료 기록 | `id`, `date`, `endedAt`, `status`, `bestOf`, `results`, `games`, `roster`, `draw`, `teamNames` 등 | 그 시점의 선수·팀·세트 스냅샷. `status`는 `completed` 또는 `stopped`. |

`winner`와 팀 번호는 `0` 또는 `1`, `role`은 `top / jungle / mid / adc / support`다. 화면에서는 TOP 등으로 표시할 수 있다. `damage`는 **챔피언에게 가한 총 피해량**, `vision`은 **시야 점수**다. 총 피해량·받은 피해량과 혼용하지 않는다.

현재 저장 한도는 UTF-8 JSON 기준 **1.5 MiB**, 기록 배열의 도메인 상한은 5,000개다. 보통 용량 한도가 먼저 문제가 될 수 있다. 크기 초과 저장은 기존 데이터를 변경하지 않고 거절한다. 새로운 대용량 요구가 생기면 단순히 프런트 제한을 없애지 말고 저장 구조를 검토한다.

## 3. 통계의 단일 원천과 계산 규칙

개인 통계의 단일 원천은 현재/종료 경기의 **플레이된 세트 기록**이다. `selectGames`, `selectPlayers`, `selectPlayer`는 읽기 전용이고 별도 통계 테이블은 없다. 현재 시리즈와 같은 ID의 아카이브는 중복 합산하지 않으며 현재 결과가 우선한다. 수정·삭제·복원 후 같은 selector를 다시 실행하면 모든 집계가 바뀐다. 다른 열린 탭은 가시 상태에서 15초 갱신 또는 수동 새로고침으로 최신 상태를 받는다.

| 계산 함수 | 규칙 |
|---|---|
| `calculateWinRate` | 승 / 유효 세트 수 × 100. 경기 0건이면 `null`. |
| `calculateKDA` | (K+A)/D. K/D/A 모두 알려진 경우만 계산. D=0이면 `perfect: true`, 비율은 `null`. |
| `aggregateStats` | 누적 KDA는 K/D/A가 모두 있는 동일 표본의 합계로 계산. 경기별 KDA의 산술평균이 아니다. |
| `calculateAverageStats` | 항목별로 알려진 값만 평균. 항목별 `samples`를 함께 유지한다. |
| `calculateCsPerMinute` | CS와 양수 경기 시간이 둘 다 있는 동일 경기들의 총 CS / 총 시간(분). 시간 없는 경기는 이 지표에서만 제외한다. |
| `aggregateByPosition` | 각 세트에 고정된 실제 `role`로 집계. 등록 주/부 라인을 대입하지 않는다. |
| `aggregateByChampion` | 실제 챔피언 문자열로 집계하고 기본 경기 수 내림차순. 미수집 챔피언은 그룹에서 제외한다. |
| `getRecentForm` | 최신순 결과, 최근 최대 5경기, 연승·연패. 날짜 → 시리즈 시각/ID → 세트 번호로 결정적인 정렬. |

`null`은 미수집, `0`은 실제 0이다. 취소·무효 경기는 selector에서 제외한다. 잘못된 중복 선수·팀·결과 구조는 검증에서 거절한다. 기존 기록의 누락된 선택 측정치는 `null`로 정규화하며, 명시적으로 잘못된 `games` 배열을 정상 과거 기록으로 가장해 복구하지 않는다.

UI 자릿수는 승률·CS/분 1자리, KDA 2자리, 평균 K/D/A 등 1자리다. 추이 차트는 미수집 지점을 끊고 Perfect KDA를 유한한 숫자 값으로 변환하지 않는다. 필터를 바꿔도 프로필 상단의 날짜 범위 전체 요약과 탐색 영역의 선택 범위를 명확히 구분한다.

## 4. 외부 JSON 등록과 선수 식별

사이트는 사진을 분석하지 않는다. 관리자 화면에서 해당 시리즈/세트를 고른 후 **프롬프트 복사 → 외부 에이전트에 사진 전달 → JSON 붙여넣기/파일 선택 → 연결·검증 → 미리보기 → 확인 저장**으로 진행한다. 프롬프트는 현재 대상 경기의 선수 ID·실명·닉네임 매칭표를 포함하므로 임의의 오래된 템플릿을 재사용하지 않는다.

외부 JSON v1은 아래 키가 전부 있어야 하고, 미수집 항목은 키 생략 대신 `null`을 넣는다. 알 수 없는 추가 키는 거절한다.

| 위치 | 필수 키 / 제약 |
|---|---|
| 최상위 | `schemaVersion: 1`, `seriesId`, `matchDate`, `gameNumber`, `externalId`, `winner`, `durationSeconds`, `notes`, `players` |
| `players` 각 항목 | `playerId`, `nickname`, `team`, `role`, `champion`, `kills`, `deaths`, `assists`, `damage`, `cs`, `gold`, `vision` |
| 배열·크기 | 참가자 정확히 10명, 입력 텍스트 최대 256 KiB. |
| 경기 시간 | `null` 또는 1~21,600초의 정수. |
| 수치 | 음수가 아닌 정수 또는 `null`. K/D/A 각각 최대 1,000, damage/gold 각각 10,000,000, cs/vision 각각 100,000. |
| 승자·팀·라인 미확정 | 입력에는 `null` 허용. 실제 저장 전 관리자가 기존 라인업과 일치하도록 확정해야 한다. |

다른 시리즈 JSON, 선수 중복/누락, 확정 라인업과의 불일치, 중복 `externalId`는 거절한다. 종료 기록의 기존 세트는 보강할 수 있지만 새 세트를 뒤에 추가할 수 없다.

실명·닉네임 연결 원칙은 다음과 같다.

1. `playerId`를 통계의 식별자로 유지한다. 외부 입력의 `nickname`은 사진에 보이는 원문이며 저장 시 `nicknameAtMatch`가 된다.
2. ID가 없으면 기존 실명·현재 닉네임·확인된 별칭에 **유일하게 정확히 일치**할 때만 자동 연결한다. NFKC·대소문자·공백은 정규화하되 Riot `#태그`는 유지한다.
3. 미등록 ID, 오탈자, 중복 이름, ID와 다른 사람을 가리키는 닉네임은 관리자 확인으로 넘긴다. 유사 이름은 후보일 뿐 자동 확정하지 않는다. 새 선수를 자동 생성하지 않는다.
4. 닉네임 변경은 현재 닉네임을 바꾸고 이전 이름을 별칭에 보존한다. 선수 ID와 과거 경기 닉네임은 바뀌지 않는다.
5. JSON 등록 중 원문 닉네임을 별칭으로 기억하는 옵션은 기본 꺼짐이다. 관리자가 확인한 경우에만 적용하며 현재 닉네임을 덮어쓰지 않는다.
6. 현재 등록 선수가 있으면 현재 닉네임 원장을 우선한다. 예전 아카이브의 오래된 별칭으로 삭제한 별칭을 되살리지 않는다. 과거의 잘못된 경기 닉네임은 기존 기록 편집/감사 흐름에서 고친다.

## 5. 권한·API·동시 저장

호스팅 공개 범위와 앱 편집 권한은 별개다. 현재 사이트는 공개 조회이며 로그인했다고 관리자가 되지 않는다. `app/chatgpt-auth.ts`는 Sites가 전달한 신뢰된 인증 헤더에서 사용자 ID를 읽는다. 클라이언트의 `role` 값으로 권한을 부여하지 않는다.

| API | 허용 범위 |
|---|---|
| `GET /api/session` | 세션·역할 확인. 미로그인 사용자는 viewer. |
| `GET /api/state` | 조회 사용자. 공용 경기 상태와 revision 반환. |
| `PUT /api/state` | owner/admin. `{ state, expectedRevision, reason? }` 검증 후 저장. |
| `GET /api/audit?recordId=...` | owner/admin. 최근 최대 50개 기록 변경 이력. |
| `GET /api/admins` | owner만 관리자 목록 조회. |
| `POST /api/admins`, `DELETE /api/admins` | owner만 관리자 부여/회수. |

소유자는 런타임 비밀 설정 `OWNER_EMAIL`과 최초 일치하는 신뢰된 로그인 사용자의 **고정 사용자 ID**에 한 번 연결된다. 관리자 이메일 부여도 첫 로그인에서 사용자 ID에 고정된다. 이후 같은 이메일의 다른 ID가 권한을 승계하지 않는다. 앱에서 소유자 권한을 삭제할 수 없다.

쓰기에는 같은 origin, `application/json`, 최대 요청 본문 10 MiB, 도메인 검증을 적용한다. 서버는 저장 시점에 SQL 조건으로 관리자 권한과 revision을 다시 확인한다. 다른 관리자가 먼저 저장하면 `409 revision_conflict`, 권한이 회수되면 `403`을 반환한다. 충돌 후 최신 데이터를 다시 읽고 편집을 재적용해야 하며 자동 덮어쓰기로 우회하지 않는다.

`shared_state` 변경과 `record_audit` 삽입은 하나의 D1 `batch` 트랜잭션이다. 서버가 실제 변경 전후 아카이브·행위자·시각·사유를 기록한다. 클라이언트가 감사 행을 제출할 수 없고 감사 삽입 실패 시 상태 저장도 롤백된다. 이전 기록 복원 역시 새 감사 이력을 남긴다.

## 6. 데모와 향후 확장

`public/player-demo.js`는 `haeram`의 가상 24경기를 브라우저 메모리에서 만든다. `players.html?player=haeram&demo=1`은 실제 API 읽기를 건너뛰고 데모 selector 결과만 표시한다. 운영 데이터 저장·백업에 합치지 않으며 데모에서 나올 때 실제 상태를 다시 읽는다. 다른 가상 참가자는 데모 이름으로 표시한다.

현재 `performanceScore`, `internalMMR`, `mvp`, `ace`, `damageTaken`, 와드 데이터, `objectiveDamage`는 저장/산정하지 않는다. 미수집 값의 0점 패널도 없다. 확장할 때는 다음 순서로 바꾼다.

- `history-core`의 허용 필드·상한·clone/upgrade와 과거 데이터 호환성.
- `import-core`의 버전 계약·프롬프트·미리보기 및 기록 편집 UI.
- `player-stats`의 표본 정의·selector와 null/0 테스트.
- 프로필 UI의 표시 조건. 새 점수는 산식 버전·최소 표본·설명 기준을 먼저 확정한다.
- 셔플과 연결할 경우 별도 adapter를 둔다. 승인된 공식 없이 기존 티어 가중치에 누적 승률 등을 섞지 않는다.

## 7. 소스 ZIP과 운영 백업의 경계

이 ZIP은 소스·설계·작업 현황의 인수인계 자료다. **운영 D1의 경기 기록, 감사 이력, 관리자 부여, 소유자 연결, 비밀 설정은 포함하지 않는다.** 테스트/데모 자료는 운영 경기 데이터가 아니다.

앱의 전체 JSON 백업에는 현재 상태·선수 원장·경기 아카이브가 들어간다. 별도 D1 테이블인 `record_audit`, `admin_grants`, `site_settings`는 포함하지 않는다. 운영 이관 시 경기 백업/가져오기와 권한·감사 이력의 보존을 구분해 계획해야 한다. 로컬의 기존 브라우저 기록은 관리자가 명시적으로 가져오기 전까지 자동 업로드하지 않는다.
