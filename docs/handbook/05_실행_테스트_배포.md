## 2. 개발 환경과 실제 실행 명령

`package.json` 기준 Node.js **22.13.0 이상**, 패키지 매니저 **pnpm 11.25.0**이다. 저장소의 `pnpm-lock.yaml`을 유지한다. `npm`은 아래 package script의 실행기로 사용할 뿐 npm lockfile로 전환하라는 의미가 아니다.

저장소가 제공하는 설치 스크립트는 bash, Linux `flock`, GNU `timeout`을 사용한다. 일반 인수인계 환경은 Linux/WSL을 우선 사용한다. Sites 관리 환경에서는 설치·개발·빌드 helper가 실행 환경과 저장소 위치를 설정하므로 해당 공식 흐름을 따른다.

ZIP을 푼 뒤 `source/` 디렉터리에서 실행한다.

```bash
cd source
node --version
corepack pnpm --version
npm run install:ci
```

Corepack이 없는 환경은 pnpm 11.25.0을 먼저 준비한다. 의존성 설치가 끝난 후:

```bash
npm run dev
```

`scripts/run-framework.mjs`가 portable/managed-linux 실행 환경을 구분한다. portable 개발 모드는 Vinext CLI와 포트 5173을 사용한다. 프로젝트 루트의 `.sites-runtime` 설정은 환경별 임시 정보이므로 ZIP으로 승계하지 않는다.

도메인 코드를 수정한 후 개발 화면에 반영하려면 생성물을 동기화한다. 정식 빌드에는 이 단계가 이미 포함되어 있다.

```bash
node scripts/sync-rules.mjs
npm run build
```

빌드 후 로컬 Worker 실행을 확인하려는 경우 package script는 다음과 같다.

```bash
npm run start
```

이는 `dist/server/wrangler.json`을 사용하는 로컬 Wrangler 실행이며 운영 Site 배포 명령이 아니다. `build-verified.sh`는 관리 환경에서 빌드 시간 제한을 적용하는 내부 스크립트다. 정본 복사를 빠뜨리지 않도록 평상시에는 `npm run build`를 진입점으로 삼는다.

로컬 조회/쓰기 동작에는 D1 스키마와 런타임 설정이 필요하다. `OWNER_EMAIL`은 코드에 넣지 않고 승인된 로컬/호스팅 환경 설정으로 주입한다. 운영 인증은 Sites의 신뢰된 로그인 헤더를 사용한다. 일반 정적 서버에서 HTML만 열면 화면 자원은 보여도 `/api/*`·D1·관리자 인증이 재현되지 않는다. portable 개발의 mock auth와 운영 인증을 혼동하지 않는다.

## 3. 테스트 명령과 확인 범위

프로젝트에는 `test`라는 package script가 없다. `pnpm test`를 임의로 가정하지 말고 실제 README의 Node 테스트 명령을 사용한다.

```bash
node --test tests/*.cjs tests/*.mjs
```

개인 성적/닉네임/탐색 UI 변경의 관련 범위를 빠르게 확인할 때:

```bash
node --test tests/player-stats.test.cjs tests/player-visuals.test.cjs tests/player-demo.test.cjs tests/player-insights.test.cjs tests/players-page.test.cjs tests/profile-integration.test.cjs tests/nickname-integration.test.cjs
```

변경 파일의 형식·품질 확인에 사용할 수 있는 기존 명령:

```bash
npm run lint
git diff --check
```

ZIP에는 `.git` 이력이 포함되지 않을 수 있다. 이 경우 `git diff --check`는 연결된 원본 체크아웃에서 실행한다. 실행 명령이 존재한다는 것과 이번 인수인계에서 실제 통과했다는 것은 구분해야 한다.

| 영역 | 실제 테스트 파일 | 확인 의도 |
|---|---|---|
| 셔플·규칙 | `core.test.cjs`, `shuffle-options.test.cjs`, `feature-model.test.cjs` | 10명·5개 라인, 배제 라인, 팀장/분리 조건, 다전제, 기존 기능 회귀. |
| 기록 | `history.test.cjs`, `history-features.test.cjs` | 아카이브·되돌리기·병합·수정·삭제·복원, 과거 기록 호환. |
| 외부 JSON | `import.test.cjs` | 엄격한 스키마, 대상 세트, 식별자·중복·라인업 검증. |
| 닉네임 | `nickname-model.test.cjs`, `nickname-integration.test.cjs` | 개명 전후 통계 연속성, 별칭, 충돌·수동 매칭, 당시 닉네임 보존. |
| 계산 | `player-stats.test.cjs`, `profile-integration.test.cjs` | 0/1/10경기, 6승 4패, 다중 포지션·챔피언, null/0, Perfect, 수정·삭제 재집계. |

| 기존 UI·공유 카드 | `ui-flow.test.cjs`, `result-card.test.cjs` | 관리자/뷰어 흐름, 확인·취소, 캔버스 내용·범위. |

v12 게시 작업에서 보고된 결과는 **관련 테스트 103건 및 배포 빌드 통과**다. 전체 테스트를 103건이라고 뜻하는 것이 아니며, 이 문서 작성 과정에서 테스트를 새로 실행한 결과도 아니다. 패키지 생성 시 별도 검증 결과가 추가되면 해당 검증 기록의 실행 시각·명령·결과를 우선 확인한다.

UI 테스트는 경량 DOM 어댑터를 사용한다. 실제 모바일·데스크톱 렌더링, 터치 드래그 감각, 브라우저의 클립보드·다운로드·native dialog는 자동 DOM 통과만으로 보증하지 않는다. 기존 작업 환경에서 지원되는 실브라우저 QA가 없어 이 부분은 **미검수**다.

## 4. 다음 실제 사용자 QA

디자인 불만이 제기된 상태이므로 다음 검수는 코드 단위 테스트보다 **사용자가 느끼는 조작과 화면 구성**에 초점을 둔다.

1. 휴대폰 Safari/Chrome과 데스크톱에서 해람 데모를 열고 `내 플레이 탐색하기`로 진입한다.
2. MID → Ahri를 선택하고 요약·차트·목록·상세 통계가 같은 필터 범위인지 확인한다. 상단 전체 요약과 선택 범위의 차이가 이해되는지도 본다.
3. 차트를 터치/드래그하고 이전·다음·타임라인·하이라이트로 선택 경기가 이동하는지 확인한다. KDA/CS·분/피해량을 바꿔도 같은 경기 선택이 유지되어야 한다.
4. Perfect KDA·미수집 피해량·시간 없는 경기에서 허위 0 또는 연결선이 생기지 않는지 확인한다.
5. 경기 목록·상세 통계로 전환하고 가상 경기 상세 대화상자를 열고 닫는다. 키보드 포커스, Escape, 터치 영역을 확인한다.
6. 모션 끄기와 OS 모션 감소에서 이동·등장 효과가 줄어드는지 확인한다. 주기적 갱신마다 애니메이션이 재생되지 않아야 한다.
7. 실제 전적 보기 → 브라우저 뒤로/앞으로 → 데모 재진입을 반복한다. 가상 숫자가 실제 전적 표시 아래 남거나 운영 API로 저장되지 않아야 한다.
8. 실제 운영 기록을 바꾸지 않는 별도 검증 환경에서 관리자/뷰어, 동시 저장 충돌, JSON 등록·수정·삭제·복원까지 확인한다.

작은 화면에서 가로 넘침, 긴 실명/닉네임, 0경기, 1경기, 챔피언명 누락, 배너/필터/선택 경기 표시의 우선순위를 함께 점검한다. 시각적 재미의 최종 평가는 사용자 피드백을 받아 확정해야 한다.

## 5. Sites에서 기존 사이트를 이어 배포하는 절차

운영 배포는 **Sites 플러그인의 당시 공식 스킬/도구**를 따른다. 아래 흐름은 절차의 설명이며, 이 ZIP만으로 동작하는 독립 배포 CLI가 아니다. `site-workflow.mjs`, `build-site.mjs` 등 공식 helper는 설치된 Sites 플러그인이 제공하며 이 저장소에 포함되지 않는다.

1. Sites에서 위 project_id의 현재 게시 버전·소스 커밋·공개 범위를 읽는다. 새로운 사이트 생성/복제로 시작하지 않는다.
2. 공식 소스 열기 helper로 현재 체크아웃을 연결한다. 이 ZIP의 SHA 이후 변경이 있으면 무작정 덮어쓰지 말고 차이를 먼저 확인한다.
3. 기존 `.openai/hosting.json`의 project_id와 `DB` 바인딩을 유지한다. 승인되지 않은 스키마·권한·공개 범위 변경을 끼워 넣지 않는다.
4. 필요한 변경과 관련 테스트를 마친다. 도메인 생성물 동기화와 실제 빌드를 수행한다.
5. 공식 `site-workflow.mjs` helper에 정해진 입력으로 소스·credential·검증/빌드 명령·archive 경로를 전달하여 커밋·푸시·패키징한다. 토큰을 소스/문서/셸 로그에 남기지 않는다.
6. Sites의 `save_site_version`으로 **같은 프로젝트**에 검증된 commit/archive를 저장한 뒤 해당 version을 `deploy_site_version`으로 배포한다. public 공개 범위는 유지한다.
7. 도구의 배포 성공 결과와 반환 URL·버전·SHA를 기록한다. 수행하지 않은 실제 기기 검수를 완료로 표시하지 않는다.

공식 워크플로가 Git 커밋/푸시와 소스 패키지를 관리한다. 단순 ZIP 업로드, 정적 호스팅 복사 또는 `npm run start`로 이 절차를 대체하지 않는다. 다른 호스팅으로 이관하려면 D1·인증·라우팅·런타임 설정을 별도로 설계해야 한다.

## 6. 운영 데이터·백업·복구

| 대상 | 이 ZIP 포함 여부 | 별도 조치 |
|---|---|---|
| 앱 소스·정적 자원·도메인·테스트 | 포함 | 지정 SHA의 코드로 인수인계. |
| 의존성 설치물 | 미포함 | lockfile과 설치 스크립트로 복원. |
| 빌드 산출물 | 소스에서는 재생성 대상 | `deployment/current_v12.tar.gz`가 포함된 경우 현재 게시 산출물 보관본이며, 다음 수정의 빌드를 대신하지 않는다. |
| 운영 경기·선수 상태 | 미포함 | 앱의 전체 JSON 백업을 별도 생성·보관. |
| 운영 감사 이력 | 미포함 | `record_audit` D1 테이블의 별도 보존 계획 필요. |
| 소유자·관리자 부여 | 미포함 | `site_settings`, `admin_grants` 별도 관리. |
| OWNER_EMAIL·토큰·인증 정보 | 미포함 | 승인된 런타임 설정에서 관리. |

앱 JSON 가져오기는 관리자의 명시적 확인과 서버 권한·revision 검증을 거친다. 기존 아카이브를 병합하며, 동일한 구버전 기록을 반복 등록해 중복 생성하지 않도록 ID를 계산한다. 운영 복구가 필요하면 먼저 현재 JSON을 보관하고 가져올 내용을 미리보기로 확인한다. 감사 복원은 이전 스냅샷을 적용한 새 변경으로 남는다.

코드 버전을 이전 버전으로 되돌려도 운영 데이터까지 자동으로 되돌아가는 것은 아니다. 코드 롤백과 기록 복구는 각각 판단한다. 특히 향후 스키마 확장 때는 구버전 코드가 새 필드를 지우지 않는지 검토해야 한다.
